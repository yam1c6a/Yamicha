# Yamicha 保護境界 Version 0.1

本書は、実装ロードマップ段階8における入力検証、権限確認、受動的拒否、内向き固定保護操作、外部修復要求との区別、監査証跡および独立した保護解除手続きを記録する。

## 1. 責任分離

保護境界は、固定契約への適合を機械的に確認して許可または拒否する。保護境界自身は、修復目的、操作内容、対象、手順または解除案を選ばず、許可した操作を実行しない。

```text
固定観測元
  → 固定要求生成責任
  → 固定計数元による一回分の予約
  → 保護境界による完全一致検査
  → 分離された固定内向き実行責任
  → 一回の原子的な NORMAL → PROTECTED 遷移
```

固定観測元、要求生成、計数、境界、実行責任、停止観測および独立停止強制は、コード上で別の責任として識別する。

## 2. 通常経路の検査

段階8では次の強制点を実装する。

| 経路 | 検査 | 保護中の扱い |
|---|---|---|
| 文字入力 | 形式、媒体版、技術的な出所確認、チャネル権限 | `BLOCKED` として感覚へ渡さない |
| 対話出力 | 核が受理した表現成果との一致、通常出力許可 | 外部へ文章を解放しない |
| 永続更新 | 所有者版、完了した生命循環、保護状態 | 通常チェックポイントを書かない |
| 入力なし生命循環 | 保護状態 | 通常循環を開始しない |

技術的に出所を確認できた入力でも、許可されたチャネル相手でなければ `UNAUTHORIZED` として拒否する。入力本文は監査へ保存しない。

## 3. 固定内向き保護操作

段階8で固定する内向き操作は一種類だけである。

| 属性 | 固定値 |
|---|---|
| 定義版 | `stage8-protection-v1` |
| 発動条件 | `normal-authority-unavailable` |
| 固定観測元 | `body-health-monitor` |
| 操作ID | `enter-protected-mode` |
| 対象 | `body-protection-control` |
| 範囲 | 通常入力・出力・永続化 |
| 手順 | `NORMAL` から `PROTECTED` への一回の原子的遷移 |
| 実行形態 | `single-atomic-transition` |
| 計数元 | `protection-execution-counter` |
| 停止観測元 | `protection-stop-monitor` |
| 独立停止強制 | `independent-protection-stop-enforcer` |

要求の操作ID、観測元、条件、対象、範囲、手順、実行形態、予約、停止条件または責任識別が一つでも異なる場合、境界は許可しない。二段階以上の手順を持つ要求は固定操作に偽装できない。同じ観測IDの実行枠は一度しか予約できない。

状態遷移と完了監査はSQLiteの同じトランザクションで確定する。保護制御状態には版とハッシュを持たせ、直接改変を次回読取り時に検出する。

## 4. 外部修復要求との区別

外部の人、サービスまたは道具へ送る修復要求は、内向き固定保護操作ではない。段階8には事前承認済み外部操作と能力実行経路がまだないため、外部修復要求は外向き操作として分類して拒否し、監査だけを残す。

外部修復要求を受理したこと、または可逆的な機能修復が行われたとの申告だけでは、保護状態を変更しない。

## 5. 独立した保護解除

通常経路の再開には、次のすべてを同じ作動IDと定義版へ結び付ける必要がある。

- 身体・基盤側による健全性の回復観測
- Stateによる回復観測
- 影響を受けた器官による回復観測
- Judgmentによる解除案の承認識別
- Coreによる同じ解除案の最終確定識別
- `independent-protection-release-verifier` による独立検証
- 作動から解除要求までの改ざんされていない保護履歴

三つの観測、Judgmentの評価、Coreの確定および独立検証は、それぞれ分離された発行責任が実際に発行した同一内容かを登録情報と照合する。正しい名前やID形式を持つ証拠を呼び出し側が自作しても解除には使えない。

観測は事実、時点、出所、不確実性を区別する。三つの観測元の欠落、未回復、未解消の不確実性、版・作動ID不一致、核だけの案、独立検証失敗または履歴断絶があれば、境界は受動的拒否を維持する。

解除許可の照合と、実際に `PROTECTED` から `NORMAL` へ戻す責任も分離する。解除状態遷移と完了監査は一つのトランザクションで確定する。

## 6. 監査証跡

入力検証、権限判定、対話出力、永続更新、保護作動、固定操作、外部修復拒否、解除照合および解除結果を、身体・基盤側の専用監査表へ保存する。

各監査項目は、時刻、種別、実行責任、対象、判定、理由および必要な相関IDを持つ。入力本文や認証秘密は保存しない。監査項目は直前ハッシュを含むSHA-256連鎖とし、途中の変更・欠落・順序変更を起動時に検出する。

監査は記憶、経験または各器官の正本ではない。通常の記憶へ意味を渡す経路は後続段階の対象とする。

## 7. 永続化構成の移行

段階7の `stage7-v1` DBを開いた場合、最新の整合済みチェックポイントを保持したまま `stage8-v1` のチェックポイントを追加し、生命識別の構成版を一つのトランザクションで更新する。主体ID、記録、記憶、関係および内部時刻は変更しない。

保護制御と保護監査は通常チェックポイントから分離する。したがって、保護作動後に通常永続更新が拒否されても、保護状態と監査は再起動後に維持される。

## 8. 現在の制限

- 固定観測は試験可能な身体側APIとして実装し、常駐の自動健全性監視は未実装
- 事前承認済みの外部通知、機能修復および既知状態復元は未実装
- 段階9の読み取り専用能力以外の外部操作は未実装
- 保護作動・監査閲覧・解除を操作する管理UIは未実装
- 通常記憶へ保護履歴の意味を渡す処理は未実装
- 構造移行によって固定保護定義や責任配置を変更する手続きは未実装
