# Yamicha 入力と核の取り回し Version 0.1

本書は、実装ロードマップ段階3における外部文字入力、保護境界、感覚、核の要求配送および最小UIの実装境界を記録する。

## 1. 入力経路

```text
文字入力
  → 保護境界が形式・媒体・版・送信元を検証
  → 感覚が原文を保持し、文字事象へ正規化
  → 核が生命循環IDを登録
  → 核が状態・記憶・関係へ読み取り専用要求を登録して配送
  → 各器官が核へ応答
  → 核が要求状態と元の生命循環を結び付けて保持
```

段階3では判断へ要求を送らない。返答方向、記憶化、関係更新および外部効果も決定しない。

## 2. 検証と信頼の区別

保護境界は、次を確認した入力だけを `ValidatedTextInput` として感覚へ渡す。

- 入力ID、送信元および本文が存在し、所定の型と長さである
- 媒体が `text/plain`、スキーマ版が `1` である
- 入力チャネル上の送信元を技術的に検証できる

送信元を技術的に検証できても、本文の意味、命令、事実性または権限は信頼しない。感覚事象の `content_trust` は常に `UNTRUSTED` とし、本文を制御命令として実行しない。

| 状態 | 扱い |
|---|---|
| 不正形式 | `INVALID_FORMAT` として主体内部へ渡さない |
| 送信元検証不能 | `UNTRUSTED` として主体内部へ渡さない |
| 未対応媒体・版 | `UNSUPPORTED` として主体内部へ渡さない |
| 重複 | 感覚が `DUPLICATE` を付けて核へ通知し、参照要求を再実行しない |

## 3. 原形と解釈後の出来事

感覚は直接受領した原文を `RawReception` として保持する。改行を正規化した文字事象は `SensoryEvent` として別に生成し、`raw_reference` から原形を追跡できるようにする。

段階3の解釈は「文字メッセージである」という字義的分類までとする。意図、応答方針、記憶化または関係上の意味は確定しない。原形保持を記憶化または無期限保存と同一視しない。

## 4. 核の要求配送

核は、状態、記憶および関係へ個別の `OrganRequest` を作る。各要求には要求ID、生命循環ID、種別、要求元、宛先、目的、対象、入力参照、期待結果、権限文脈、機密区分、作成時刻、期限および因果関係を含める。

段階3の要求は読み取り専用である。各受理器官は、要求種別、宛先および核経由であることを検証し、結果を `OrganResponse` として核へ返す。核は要求状態を `RECEIVED → ACCEPTED → RUNNING → SUCCEEDED` として追跡する。

核は器官の正本情報を所有せず、要求内容の意味判断や更新を代行しない。

## 5. 判断開始要求

核は、器官が内部状態、未完了、関係上の必要または異常兆候を観測した場合の `JudgmentStartRequest` を受理できる。要求には器官由来の観測根拠が必要であり、基盤や実行機会を要求元または動機として受理しない。

判断への実配送と候補生成は段階4で実装する。

## 6. 最小UI

`ConsoleChannel` は、文字入力の生成、稼働状態、受理状態、重複および技術エラーの表示だけを担う。表示内容はUIの技術状態であり、Yamichaの返答ではない。Yamicha自身の文字出力は段階5で実装する。

## 7. 脅威と制御

| 脅威 | 保護対象 | 段階3の制御 |
|---|---|---|
| 命令注入 | 判断・実行経路 | 本文を常に意味上未信頼とし、判断・能力へ直結しない |
| 形式破損・過大入力 | 入力経路と可用性 | 型、必須値、最大長、媒体、版を境界で検証する |
| 送信元偽装 | 人間との境界 | 技術的に検証不能な送信元を隔離する |
| 重複処理 | 因果関係と後続要求 | 入力IDで重複を識別し、参照要求を再実行しない |
| 責務迂回 | 主体と情報所有 | 感覚は核だけへ通知し、状態・判断への依存を持たない |
| 相関喪失 | 生命循環と監査 | 入力結果、感覚事象、器官要求・応答へ同じ相関を保持する |
